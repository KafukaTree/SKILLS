# Tech Milestones — 技术发展脉络与节点清单调研

把"某技术领域从起点到今天的演进"整理成**可溯源、学术技术向**的节点清单/资料索引,供用户深入调研文献。本技能沉淀自一次完整实战:LLM 发展史节点清单(2017-06 → 2026-08),约 180 条节点、180+ 验证链接、4 个并行调研子代理。

## 适用范围

- ✅ 技术发展史 / 发展脉络 / 里程碑节点 / 时间线清单 / 领域演进综述的资料搜集
- ✅ 需要精确日期 + 权威链接的文献索引
- ✅ 用户后续会自行深入调研的场景(清单是"索引"而非"论文")
- ❌ 不适用:完整学术论文撰写(用 auto-research)、纯政经/新闻综述

## 核心原则

1. **知识截止纪律**:当前日期之后的内容一律视为未知,必须联网核实;记忆中的日期/ID 一律视为"待验证",不得直接输出。
2. **学术技术向优先**:论文、技术报告、架构/算法/训练方法、基准、开源技术栈是主体;融资/估值/管制/收购/人事等政经条目默认剔除(除非用户点名要)。
3. **每条必须可溯源**:精确日期(年-月-日)+ 一句话技术说明 + 完整可点击链接。arXiv 论文给 `https://arxiv.org/abs/ID` 全链接,不给裸 ID。
4. **先分类再调研**:按"我的知识截止"为界划分时段——截止前(高置信,可直写但要标注)与截止后(必须调研)。需要核实的事件多、跨度大时,用并行 scout 而非串行搜索。
5. **与用户确认口味**:动工前确认"学术技术向 vs 综合向"、链接严谨度、交付格式(对话/文件)。用户说"轻量"就控制篇幅。

## 工作流

### Phase 1 — 范围与切分
- 明确:时间范围、地理/机构范围(可选)、学术向还是综合向、交付物形式。
- 把时间轴切为 **[知识截止前]** / **[截止后]** 两段;截止后按自然时段(年/半年)拆给 scout。

### Phase 2 — 并行调研(截止后时段)
- 每个时段派 1 个 `scout`(只读),`task` 批一次性发出(上限 32,实际 2–6 个足够)。
- 任务书必须**自包含**(scout 看不到本会话),格式见 `scout-task-template.md`。
- 公共约束放 batch 的 `context`,时段清单放各自 `task`;每个任务书给足主题清单、验证规则、输出格式、验收标准。
- 我自己(主代理)同时动笔写知识截止前的部分,不空等。

### Phase 3 — 交叉验证
- scout 返回后,对**最关键的条目**(尤其是超出我知识的新事实)亲自复核:直读 arXiv 页面、官方博客,或至少一次独立搜索。
- 两个 scout 的结论冲突时以一手来源(arXiv/官方文档)为准。

### Phase 4 — 组装与交付
- 按年份章节 + 年度技术主线总结组织;条目格式统一(见"输出格式")。
- 无链接条目清零(交叉引用条目也给指向链接)。
- 交付时说明:哪些部分经联网核实、核实中纠正了哪些我记忆里的错误、链接验证方式。

## Scout 任务书设计要点(易错)

1. **自包含**:目标、主题清单、硬性规则、输出格式、验收标准全部写进任务书;scout 没有会话上下文。
2. **主题清单要完整且防截断**:任务文本里避免裸引号/特殊字符导致截断(实战中两次出现主题清单被截断,需补发)。发送后立即检查 spawn 成功与任务完整性;截断了就 `hub send` 补发。
3. **要求输出完整可点击 URL**:"arXiv 论文给 https://arxiv.org/abs/XXXX 完整链接;官方博客给完整页面 URL;链接必须真实存在,不要拼造"。否则 scout 会偷懒给 ID 或域名。
4. **禁止编造条款**:明确"你记忆中的内容必须经 web_search 核实后才能输出;核实不到的标 [未核实] 并尽量排除"。这条能挡住大量幻觉。
5. **主题分组输出**:要求按主题分组(而非单一大列表),便于整合。
6. **让 scout 纠错**:把"我列出的候选日期/ID"给 scout 并明示"若与实际不符,以你的核实为准并注明差异"——这是免费的交叉验证。
7. **催收尾要具体**:scout 会过度追求穷尽。发"用户催进度,5 分钟内收尾,已核实条目直接输出,剩余主题快速过一遍,不必穷尽"。
8. **输出丢失防护**:scout 的 yield 可能只回摘要(实战中 45 条清单正文丢失)。预防:要求 scout 同时把结果写入 `local://` 文件或直接完整输出;发现丢失立即让 scout 重发(它 idle 后可用 `hub send` 唤醒)。

## 链接验证手册(核心经验)

| 来源类型 | 验证方法 | 注意事项 |
|---|---|---|
| arXiv | `read https://arxiv.org/abs/<ID>` 直读页面 | **比搜索可靠**;标题/日期/摘要一眼确认。记忆中的 ID 常错(实战中错 8/20+),必须直读 |
| arXiv ID 记忆错误实例 | Scaling Laws for Precision 实为 2411.04330(非 2502.02539);CoT-Valve 实为 2502.09601(非 2502.09605);Dr. GRPO 出自 2503.20783(非 2507.16634) | 编号相似易混;以直读为准 |
| 官方博客(OpenAI/Anthropic/Google/Meta/Mistral/HF) | 批量 `curl -s -o /dev/null -w "%{http_code}" -L -A "Mozilla/5.0" <url>` | **WAF 陷阱**:OpenAI/GitHub 对 curl 返回 403(存在但拦截爬虫);404 才是真失效。403 的链接改用 `read` 工具验证 |
| 404 排查 | 404 后换 URL 形态:GitHub blog 旧路径失效,用 read 工具试 news-insights 新路径;官网搜索站内页 | curl 404 ≠ 链接失效(GitHub blog 对 curl 也是 WAF);read 工具能过 WAF |
| DOI | `curl -sI https://doi.org/<doi>` 或 `read`(走 CrossRef API) | doi.org 对 curl 可能 403;read 走 crossref 元数据最可靠 |
| 失效视频/页面 | 官方托管失效(Facebook 视频)时,找作者本人演讲/替代源并验证 | 验证工具:read 打开 YouTube 返回标题/频道/时长 |
| 批量验证 | 一次 bash 循环 curl 20–30 个 URL,几秒完成 | 403=存在,404=真失效,000=超时重试 |

**验证纪律**:链接要么亲自验证过(状态码/页面标题/摘要),要么标注未验证。交付时说明验证方式。所有链接必须真实存在,绝不拼造。

## 输出格式规范

```
- **YYYY-MM-DD** 名称:一句话技术说明(方法/架构/参数/基准分数,不写营销语)。[来源名](完整URL) / [arXiv:ID](https://arxiv.org/abs/ID)
```

- 分组:2017 之前铺垫(可选)→ 逐年/按年章节 → 每年末"年度技术主线"总结(4–6 条,每条一句话)。
- 补充说明类条目(交叉引用)也要给指向链接,做到"无链接条目 = 0"。
- 可附带"核实更正"小节:列出与常见传闻/初稿的日期差异及依据。
- 交付文件:单 Markdown(章节分文件 + 合并版可选);中文为主。

## 质量门(交付前逐项检查)

- [ ] 每条:日期 + 一句话技术说明 + 完整可点击链接
- [ ] 缺链接条目数为 0(脚本: `awk '/^- \*\*/{if ($0 !~ /https:\/\//) c++} END{print c+0}' <file>`)
- [ ] 截止后时段每条都经过联网核实,关键条目亲自复核过
- [ ] 政经条目已剔除(除非用户要求),学术/技术条目为主体
- [ ] 记忆中的 arXiv ID 全部直读验证过
- [ ] 年度技术主线总结存在
- [ ] 交付说明:核实范围、纠正的错误、验证方式

## 本次实战教训速查(LLM 发展史案例)

1. **切分时段**:2017–2024 我知识可靠,直接写;2025/2026 各派 1 scout——总耗时约 2 小时,其中 90% 是 scout 搜索+验证。
2. **scout 会纠正主代理的错误**:把候选日期给 scout,它发现 Claude 4 实为 05-22(非 05-06)、Grok 4 为 07-09、Qwen3-Max 为 09-24、DeepSeek R2 未发布等——这些纠错直接进终稿。
3. **政经与学术分离是用户痛点**:第一版混入融资/管制/反垄断被否,重写为纯学术技术向(论文/方法/基准/开源栈)后才满意。
4. **用户两次要求升级链接严谨度**:先"给链接"→再"给严谨可点击的完整链接"→最终"一次性全部补齐"。初始就该按最高标准做,省两轮返工。
5. **说明性条目也要链接**:交叉引用条目补指向链接,把"缺链接=0"当硬指标。
6. **动手前先问口味**:学术向 vs 综合向、篇幅、格式——一次问清,避免方向性返工。
